# Политика релизов Family Assistant

Документ описывает, как мы переводим изменения в публичный релиз и какие проверки
обязательны для перехода между стадиями в плане `v1`.

## Версионирование

Используется SemVer:

- `MAJOR` — необратимые изменения API/схемы, несовместимые миграции.
- `MINOR` — новый публичный функционал без слома обратной совместимости.
- `PATCH` — багфиксы и улучшения без изменения интерфейса.

Теги:

- `x.y.z-alpha.N` — функционал в режиме эксперимента.
- `x.y.z-rc.N` — релиз-кандидат с закрытым планом миграции/восстановления.
- `x.y.z` — production-релиз.

## Базовый цикл релиза

1. Код и тесты проходят CI на candidate-коммите.
2. Собирается проверенный runtime zip.
3. Пишется `docs/releases/<tag>.md` с:
   - изменениями;
   - рисками/ограничениями;
   - как обновить и как откатить;
   - ссылками на новые проверки.
4. Запускается upgrade-acceptance между стабильным baseline и candidate.
5. Публикуется prerelease/релиз (в зависимости от стадии).
6. Записывается пост-обновление: чек-лист в `docs/implementation-status.md` и
   `docs/vision.md` (соответствующий этап).

На практике это обычно две стадии выдачи:

- `candidate package` — технический ZIP/tag для изолированного smoke/upgrade проверки;
- `promoted package` — релиз/последующий тэг после прохождения всех гейтов этапа.

## Режимы перехода

### Переход в `v1-pre`

Этап запускается когда:

- есть стабильный release workflow (этот документ) и он применён в `docs/`;
- release pipeline собирает и проверяет candidate package на CI;
- `docs/implementation-status.md` содержит живой queue с ответственным для каждого блока;
- включена базовая инфраструктура тестирования без ручного обхода safety-гейтов.

Выходной критерий этапа:

- закрыты блокирующие риски:
  - Telegram real-channel acceptance;
  - физическая верификация сирены/доставки;
  - проверка предпосылок Mikrotik strict policy (топология/IPv4/IPv6/FastTrack/восстановление) и явная блокировка активации strict режима при отсутствии их выполнения;
  - RU/UK/EN базовые onboarding flows;
  - базовый набор карточек и уведомлений без `TODO`-блокеров;
  - зафиксированное поведение strict mode в документированном «not yet supported» состоянии.
- в `implementation-status.md` есть HA/Native/CI доказательства для каждого пункта.

### Переход в `v1-rc`

Требуется:

- migration-путь из локальной legacy-конфигурации в новый пакет;
- подтверждённый upgrade-acceptance и локальная проверка rollback;
- smoke-набор для критичных модулей (Tasks/Shopping/Alarm/Court/Network/Calendar/Today);
- все ранее критичные `v1-pre` риски закрыты с reproducible доказательствами.

### Переход в `v1.0`

Требуется:

- полная публичная документация для RU/UK/EN;
- покрытие на уровне CI + HA + frontend;
- синхронность между релизным артефактом и документацией;
- внятный rollback-диалог:
  - какие данные не перезаписываются;
  - как откатить код без потери Store;
  - как вернуться на предыдущий release.

## Обязательные проверки перед публикацией

- CI-запуск (ruff/format/type/хард-линтер/fixtures, см. текущий пайплайн).
- Тест на upgrade-acceptance (`tools/run_upgrade_acceptance.py`) для миграционной проверки.
- HA smoke-пакет для затронутых модулей.
- Проверка локализации RU/UK/EN (публичные строки, ошибки, команды, карточки).
- Проверка privacy/секретов (секретов и токенов в репозитории).
- Обновление:
  - `docs/implementation-status.md`;
  - `docs/vision.md` (если меняется план/критерий);
  - `CHANGELOG`/release note.

## Политика остановки

- Если в `v1-pre` появляется новый blocker (реальная потеря канала/устойчивая ложноположительная
  автоматика, повторяющиеся ошибки доставки/перехвата), переход в следующую стадию
  запрещён до закрытия записи с доказательствами.
- Каждое значимое изменение сопровождается ссылкой на тест/логи в файле релиза.

## Критичный журнал (публичный)

Всякая новая функциональность, которая меняет поведение безопасности,
контроля устройств/сети или механики наказаний должна иметь:

1. документированную причину;
2. тесты в `tests/`;
3. запись об impact-оценке в `docs/implementation-status.md`;
4. запись в файле релиза с рисками и условиями использования.

## Примечание по HACS

Процесс публикации в HACS остаётся неизменным: сначала стабильный release,
затем подача через HACS flow при подтверждении критериев.
