# 0.2.0-rc.2 — controls, settings and legacy parity repairs

This is a release candidate, not completion of the full vision or household
migration. The [legacy audit](../legacy-parity-audit.md) supersedes earlier broad
completeness claims. Retaining an old setting in an archive does not implement it.

## Repaired

- Native HA settings now preserve disabled provider drafts, support explicit
  credential clearing, and reject stale authorization or concurrent edits after
  provider validation. Disabled fallback/search settings remain saved without
  invoking those providers. All 46 native Options routes have a consumer audit.
- Alarm and presence editors select the member before loading that member's
  saved settings. Explicit alarm duration/volume companion entities are supported
  on the same registered siren device; saves never operate the hardware.
- Alarm commands stop progressing when acknowledgment, revocation or device
  replacement occurs during awaited companion controls. Known pre-start failures
  do not grant new ownership of a siren; uncertain attempted starts retain the
  ownership needed for a compensating stop. Existing owned output is preserved
  when renewal fails before another start.
- Cancellation before the main siren attempt restores prior ownership, including
  cancellation during the durable intent save. It still propagates as cancellation.
  Unload/stop drains the owned-output cleanup even if its worker or caller was
  cancelled; a later unrelated manual signal is not silenced as an owned alarm.
- Household changes and refreshes cannot apply stale card projections or leave
  an old busy state. Unresolved/error states do not cause automatic request storms.
- Purchase, task archive and reward refund reviews remain visible if an uncertain
  committed result moves their records into collapsed history. Retry retains the
  same operation, not a second purchase or reward decision.
- Invitation clipboard feedback is scoped to that invitation. A successful retry
  clears its previous error; late replies cannot alter a different member, home,
  user, connection or closed view.
- Telegram parsing again recognizes complete configured multiword recipients,
  slash arguments separated by whitespace, bounded relative day/week deadlines,
  and natural task-extension phrases. Negated or malformed duration expressions
  cannot silently fall back to today's clock. Relative deadlines are anchored to
  the received local date, as in the old parser.
- The historical `/forget` ambiguity is explanation-only; `/forgetphrase ID`
  explicitly disables a learned phrase. Addressed voice-only messages explain
  unsupported Telegram STT instead of silently disappearing.

## Evidence and limits

The [frontend audit](../../tests/README-control-audit.md), [native settings
inventory](../native-settings-audit.md) and [Telegram contract](../telegram-command-parity.md)
distinguish exercised behavior, source mappings and outstanding gaps. Synthetic
browser interaction is not real Telegram delivery, physical siren loudness, or
exhaustive coverage of every role/value/state combination.

All 29 old top-level declarations are accounted for, but 16 home/energy mapping
keys remain missing. Generic reviewed home controls, factual energy summaries,
kettle feedback, weekly solar-forecast comparison, Telegram STT/general vision,
scoped conversational memory, explicit kinship and a sanitized cloud patch queue
remain incomplete. The public module does not silently inherit private household
credentials or arbitrary service-execution authority.
The deeper workflow comparison also identified untransferred report qualifiers,
natural shopping quantities, multi-task/scoped-query grammar and reviewer deadlines;
rollover, correction integration and several old command meanings differ. These
remain explicit open gates, not fixes supplied by this candidate.

## Update and rollback

Store and Config Entry Options remain separate from HACS-managed runtime files.
Imported alarm schedules stay disabled/gentle/penalty-free until reviewed; this
release does not activate sirens, penalties, network policies or providers.

Before household installation, capture and verify the current runtime and HA
configuration rollback point, validate configuration, and obtain the required
restart authorization. Restore the captured prior code for a code rollback and
restart through the same approved procedure, preserving Store/Options. Verify
identities, schedules, current records, settings and transport health. Full backup
restoration is a separate explicitly approved operation. This candidate is not
automatically deployed to an existing household.
