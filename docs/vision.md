# Family Assistant — видение продукта

Статус: проектное видение, черновик 1.0  
Дата фиксации: 2026-09-06

## 1. Краткое видение

Family Assistant — публичная модульная интеграция Home Assistant для повседневной
координации семьи. Она объединяет семейные списки, задачи, будильники, правила,
поощрения, разговорного помощника, домашние рутины и опциональное управление
семейной сетью. Основными интерфейсами служат карточки Home Assistant и личный
Telegram-бот, который каждый пользователь создаёт для своей семьи.

Интеграция должна превращать сообщение или действие на дашборде в законченный,
проверяемый процесс:

```text
намерение → проверка контекста и прав → план → выполнение → подтверждение
          → при необходимости напоминание или эскалация → понятная история
```

Проект развивается как один самостоятельный HACS-компонент, а не как набор
локальных скриптов. Код и релизы публичны; настройки семьи, данные, адреса,
токены и пароли остаются только в Home Assistant пользователя и не затираются
при обновлении.

## 2. Миссия

Снизить ежедневную организационную нагрузку семьи и сделать домашние правила,
обязанности и автоматизации понятными, справедливыми и надёжными.

Family Assistant должен:

- помогать взрослым организовывать быт без постоянного ручного контроля;
- давать детям простой и доброжелательный интерфейс;
- связывать общение, расписания и устройства Home Assistant;
- объяснять каждое принятое решение;
- сохранять работоспособность основных функций без LLM и облачных сервисов;
- не выполнять опасные или неоднозначные действия на основании одной догадки
  языковой модели.

## 3. Для кого предназначен проект

Основная аудитория:

- пары, ведущие совместный быт;
- семьи с детьми;
- семьи с одним родителем;
- несколько поколений, живущих вместе;
- пользователи Home Assistant, которым нужен семейный интерфейс поверх
  автоматизаций и устройств.

Одна установка Home Assistant может содержать несколько независимых семейных
пространств. Каждое пространство имеет собственных участников, роли, правила,
бота, данные и включённые модули.

## 4. Основные принципы

### 4.1. Полезность без искусственного интеллекта

Списки, задачи, будильники, расписания, права, штрафы, поощрения и проверенные
команды работают детерминированно. LLM помогает понять необычную формулировку,
вести разговор и работать с поиском, но не является базой данных или
единственным исполнителем.

### 4.2. Модель предлагает, интеграция решает

LLM может вернуть только типизированный план с ограниченным набором действий.
Интеграция независимо проверяет участника, роль, объект, состояние, параметры и
контекст. Успех сообщается только после фактического выполнения и контрольного
чтения результата.

### 4.3. Объяснимость

Для каждого изменения доступно объяснение: кто запросил действие, как команда
была понята, какие проверки выполнены, что изменилось и можно ли это отменить.

### 4.4. Локальность и приватность по умолчанию

Публичный код не содержит пользовательских сведений. Данные семьи хранятся в
Home Assistant. Подключение внешнего LLM, поиска, Telegram или MikroTik является
явным выбором пользователя.

### 4.5. Модульность

Каждый функциональный блок можно включить или выключить. Неиспользуемый модуль
не создаёт сущности, не слушает события и не просит лишних разрешений.

### 4.6. Безопасные значения по умолчанию

Автоматические штрафы, управление устройствами, изменение сети и блокировка
доступа выключены, пока пользователь явно их не настроит и не подтвердит.

### 4.7. Надёжность важнее остроумия

Идемпотентность, отсутствие дублей, восстановление после перезапуска и честное
сообщение об ошибке важнее красивого ответа модели.

## 5. Интерфейсы пользователя

### 5.1. Home Assistant

Интеграция предоставляет сущности, действия, события, диагностику и набор
собственных карточек Lovelace. Все настройки доступны через Config Flow и
Options Flow; обычная установка не требует YAML.

### 5.2. Telegram

Каждый пользователь создаёт собственного бота через `@BotFather`. Family
Assistant не предоставляет общего публичного бота и не использует секреты
разработчика.

Мастер подключения:

1. показывает пошаговую инструкцию `/newbot`;
2. принимает токен через защищённое поле и проверяет его методом `getMe`;
3. предлагает добавить бота в семейную группу;
4. выдаёт одноразовую команду вида `/family_setup A7K4`;
5. автоматически определяет ID и название группы из Telegram Update;
6. просит подтвердить найденную группу;
7. аналогично связывает личные чаты с участниками семьи одноразовыми кодами.

Предусматриваются два режима:

- режим повышенной приватности: команды, кнопки и ответы боту;
- разговорный режим: мастер объясняет отключение Privacy Mode и необходимость
  повторно добавить бота в группу.

Токен одного бота нельзя одновременно использовать в другом poller или
webhook. Интеграция обнаруживает конфликт и показывает понятный Repair вместо
молчаливой потери сообщений.

### 5.3. Другие каналы

В дальнейшем возможны Home Assistant Companion, Assist и другие провайдеры
уведомлений. Бизнес-логика не зависит от Telegram: канал является адаптером, а
не ядром системы.

## 6. Модель семьи и права

Мастер предлагает редактируемые шаблоны:

- пара;
- родители и дети;
- один родитель и дети;
- полностью ручная конфигурация.

В шаблонах используются только универсальные имена: «Родитель 1», «Родитель
2», «Ребёнок 1». Пользователь меняет их, задаёт обращения, язык и семейные
отношения.

Базовые роли:

- владелец пространства;
- родитель/администратор семьи;
- взрослый;
- ребёнок;
- гость.

Права проверяются на серверной стороне для каждого действия. Скрытая кнопка в
карточке не считается механизмом авторизации. Участника можно связать с
пользователем Home Assistant, Telegram ID и несколькими сетевыми устройствами.

## 7. Функциональные модули

### 7.1. «Семья сегодня»

Главный экран семьи объединяет:

- присутствующих дома;
- ближайшие события и будильники;
- задачи на сегодня и просроченные дела;
- покупки;
- запросы подтверждения;
- баллы и активные последствия;
- состояние Telegram, LLM, поиска и дополнительных интеграций;
- проблемы, требующие внимания.

Карточка адаптируется к роли. Ребёнок видит собственные дела и доступные ему
действия, родитель — общую картину и ожидающие решения.

### 7.2. Покупки

Покупки имеют собственную предметную модель и не являются Todo-задачами.

Позиция содержит:

- название, количество и единицу;
- категорию и желаемый магазин;
- комментарий;
- автора и, при необходимости, покупателя;
- статус согласования;
- частичное и полное приобретение;
- историю изменений.

Возможности:

- единый семейный список;
- предложения детей с подтверждением взрослых;
- объединение дублей;
- частичная покупка;
- регулярные позиции;
- добавление текстом, голосом, фотографией или штрихкодом;
- необязательная история цены;
- связь с запасами и планом питания.

### 7.3. Задачи и обязанности

- разовые и повторяющиеся задачи;
- назначение одному или нескольким участникам;
- сроки, этапы и чек-листы;
- принятие задачи и отметка начала;
- текстовый или фотоотчёт;
- подтверждение, возврат на доработку и отмена;
- справедливая ротация обязанностей;
- напоминания и настраиваемая эскалация;
- архив без удаления истории;
- пакетные операции как одна транзакция.

Автоматическое наказание за пропуск включается отдельно и всегда имеет
стабильный идентификатор, чтобы повторная проверка не создавала второй штраф.

### 7.4. Будильники и подтверждение пробуждения

- независимые расписания будней и выходных;
- исключения для каникул, праздников, болезни и отпуска;
- привязка сирены или другого устройства;
- повторное включение сирены, пока этап не подтверждён;
- одноразовая мини-капча с защищённой кнопкой;
- повторная проверка через случайный интервал;
- сохранение активного этапа после перезапуска Home Assistant;
- статистика времени пробуждения;
- мягкий и строгий профили;
- тестовый запуск без штрафов.

Запланированное заранее сообщение, старый callback или ответ другого человека
не подтверждает пробуждение.

### 7.5. Правила, поощрения и семейный суд

Модуль объединяет журнал баллов, последствия и апелляции. Его задача — не
только наказывать, но и поощрять полезную инициативу.

- положительные и отрицательные события;
- обязательная понятная причина;
- ручные и автоматические источники;
- защита от повторного начисления;
- отмена без удаления исходной записи;
- апелляция и подтверждение вторым взрослым;
- недельные итоги;
- ограничение автоматических штрафов;
- магазин семейных привилегий;
- полностью редактируемые правила и пороги.

Никакое конкретное семейное последствие не зашивается в публичный код.

### 7.6. Разговорный помощник и интернет-поиск

Базовый режим понимает фиксированные команды без LLM. Пользователь может
подключить:

- Ollama по своему URL и выбрать модель;
- существующего conversation-агента Home Assistant;
- совместимого внешнего провайдера в будущем;
- SearXNG или иной поддерживаемый поисковый провайдер.

Мастер проверяет доступность, модели, тайм-аут и объясняет, что LLM сама по себе
не имеет доступа к интернету. Поисковые источники считаются недоверенным
текстом, фильтруются от внутренних адресов и показываются пользователю ссылками.

Разговорный модуль предоставляет стандартную conversation-сущность и
ограниченный набор LLM-инструментов. Инструменты никогда не обходят семейные
роли и проверку Home Assistant.

### 7.7. Утренние и вечерние рутины

Рутина — последовательность шагов, а не плоский список:

```text
проснуться → подтвердить подъём → умыться → проверить рюкзак → выйти
```

Шаг может иметь время, исполнителя, подтверждение, связанную сущность HA,
условие пропуска и правило эскалации. Поддерживаются семейные шаблоны и режимы
«каникулы», «гости», «болеет», «отпуск».

### 7.8. Календарь и семейная логистика

- школа, кружки, врачи, поездки и семейные события;
- повторяющиеся события;
- кто кого сопровождает;
- связанные задачи и списки вещей;
- напоминания о подготовке;
- представление через стандартные календарные сущности Home Assistant.

### 7.9. Уведомления и эскалации

Единый движок уведомлений обслуживает все модули:

- дедупликация и идемпотентные ключи;
- очередь и повтор при временной недоступности;
- тихие часы;
- личное сообщение, затем семейная группа, затем взрослый;
- ограничение частоты;
- группировка одинаковых событий;
- обязательное закрывающее сообщение после ранее объявленной проблемы;
- различение «отправлено», «доставлено», «подтверждено» и «выполнено» там, где
  канал предоставляет соответствующие данные.

### 7.10. Журнал решений и обучение на исправлениях

Журнал показывает исходное обращение, распознанное намерение, проверки,
изменения и итог. Пользователь может исправить неверно понятую команду.

Каскад понимания:

```text
строгий парсер
  → локальный словарь ранее подтверждённых формулировок
  → выбранный пользователем LLM
  → уточняющие кнопки
```

После явного исправления безопасная языковая форма сохраняется локально как
пример. Она не превращается автоматически в новое разрешение и не меняет код.

Опциональный developer mode может сформировать обезличенный диагностический
пакет или запустить изолированного агента для подготовки предложения патча.
Такой агент не получает токены, доступ к Home Assistant, RouterOS или
возможность развернуть изменение. Патч требует обычного ревью, тестов и релиза.

### 7.11. Питание и домашние запасы

- недельное меню;
- продукты и расходники дома;
- минимальные остатки и сроки годности;
- автоматическое предложение позиций в покупки;
- аллергии и семейные предпочтения;
- рецепты как подключаемый источник, а не обязательная часть ядра.

### 7.12. Школа

- расписание;
- домашние задания и контроль сроков;
- сбор рюкзака;
- напоминания о форме, материалах и событиях;
- импорт календаря или подтверждённое распознавание фотографии расписания.

### 7.13. Обслуживание дома

- сообщение о поломке с фотографией;
- назначение ответственного;
- регламентные работы;
- расходники, гарантия и документы;
- история ремонта оборудования.

### 7.14. Голосования, дайджесты и присутствие

- семейные голосования;
- персональный утренний и вечерний дайджест;
- уведомления только присутствующим или ответственным людям;
- отложенное напоминание после возвращения домой;
- запрет на критические выводы только по одному датчику присутствия.

## 8. Опциональный модуль MikroTik

### 8.1. Назначение

Модуль помогает пользователю понять, какие устройства находятся в домашней
сети, привести DHCP-лизы в порядок и управлять семейными ограничениями. Он
активируется отдельно и не требуется для остальных функций.

Первая версия ориентируется на RouterOS 7 и официальный REST API. Соединение
выполняется по HTTPS с отдельной учётной записью RouterOS. Небезопасный HTTP не
является рекомендуемым режимом.

### 8.2. Уровни доступа

Пользователь выбирает требуемые возможности:

1. **Только аудит** — чтение лизов, ARP, Wi-Fi/bridge-клиентов и Kid Control.
2. **Управление лизами** — преобразование динамических лизов и комментарии.
3. **Родительский контроль** — профили, расписания, pause/resume и лимиты.
4. **Контроль неизвестных устройств** — уведомление, карантин или строгая
   политика допуска.

RouterOS не предоставляет тонкого разграничения записи по отдельным веткам
конфигурации: право `write` шире нужных операций. Мастер обязан честно это
объяснить. Рекомендуется отдельная пользовательская группа только с необходимыми
политиками `read`, `write` и `rest-api`, без `reboot`, `policy`, `sniff`,
`sensitive`, SSH, FTP и WinBox, если они не нужны.

Даже при широком RouterOS-разрешении сама интеграция реализует только строго
разрешённый набор API-операций и не предоставляет произвольную консоль.

### 8.3. Инвентаризация устройств

Источники RouterOS:

- DHCP leases;
- ARP;
- bridge host table;
- Wi-Fi registration/access list, если точка доступа управляется MikroTik;
- Kid Control devices;
- hostname, client ID, комментарий, IP, MAC, интерфейс и время последней
  активности.

Источники Home Assistant:

- device registry и entity registry;
- MAC connections, если интеграция устройства их сообщает;
- device tracker;
- IP, hostname, производитель и модель из доступных сущностей и атрибутов;
- пользовательские названия и зона устройства.

Система строит кандидаты соответствий и показывает доказательства:

- точное совпадение MAC — максимальная уверенность;
- совпадение текущего IP и tracker — высокая, но временная уверенность;
- hostname, производитель и модель — вспомогательные сигналы;
- похожее имя сущности — только подсказка.

Предложенное имя никогда не записывается автоматически при неоднозначности.
Пользователь видит варианты, уверенность и источник каждого совпадения.

### 8.4. Преобразование динамических лизов в статические

Мастер пакетной обработки:

1. читает текущие динамические и статические лизы;
2. ищет соответствующие устройства Home Assistant;
3. предлагает понятные комментарии;
4. проверяет конфликт IP, MAC, DHCP-сервера и подсети;
5. отмечает вероятный приватный/рандомизированный MAC;
6. показывает полный план без изменений;
7. по подтверждению делает статическим только выбранные лизы;
8. считывает конфигурацию заново и подтверждает результат;
9. при частичном сбое восстанавливает уже изменённые целевые записи.

Существующие комментарии сохраняются, пока пользователь явно не выберет их
замену. Повторный запуск безопасен и не создаёт дубликатов.

Для телефона с приватным MAC мастер объясняет необходимость выбрать постоянный
адрес для конкретной Wi-Fi-сети. Сам признак locally administered MAC является
предупреждением, а не доказательством случайного адреса.

### 8.5. Родительский контроль

Участнику семьи можно назначить несколько MAC-устройств. Поддерживаются:

- недельное расписание доступа;
- разные интервалы будней, выходных и каникул;
- немедленная пауза и возобновление;
- временное продление на заданное число минут;
- ограничение скорости;
- режимы «сон», «уроки», «свободное время»;
- команды Telegram и карточка дашборда;
- журнал изменений и фактическая повторная проверка RouterOS.

Основной backend — штатный `/ip kid-control`, если конфигурация совместима.
Поскольку RouterOS реализует Kid Control динамическими firewall/queue-правилами,
интеграция не редактирует их напрямую. При ограничении скорости мастер проверяет
возможное влияние FastTrack и предупреждает пользователя.

Family Assistant изменяет только профили и устройства, которые пользователь
явно передал под его управление. Чужие RouterOS-записи остаются нетронутыми.

#### 8.5.1. Управление Kid Control через Telegram

Telegram является полноценным родительским интерфейсом MikroTik-модуля.
Владелец или участник с явно выданным правом управления сетью может писать в
личный чат бота или в авторизованную семейную группу, например:

- `что с интернетом у Ребёнка 1?`;
- `выключи интернет Ребёнку 1`;
- `включи Ребёнку 2 интернет`;
- `дай Ребёнку 1 интернет на 30 минут`;
- `разреши интернет Ребёнку 2 до 21:30`;
- `верни Ребёнку 1 обычное расписание`;
- `поставь Ребёнку 1 интернет по будням с 08:00 до 22:00`;
- `ограничь планшет Ребёнка 1 до 5 Мбит/с`;
- `какие устройства привязаны к Ребёнку 2?`;
- `покажи неизвестные устройства`.

Те же операции доступны через локализованные slash-команды и inline-кнопки.
Свободная формулировка сначала преобразуется в строгий intent с участником,
устройством, действием и сроком. Если имя относится к нескольким людям или у
человека несколько устройств и команда не охватывает их явно, бот показывает
кнопки выбора вместо догадки.

По умолчанию:

- владелец и родители могут читать состояние и менять Kid Control;
- ребёнок может видеть только собственное расписание и оставшееся время;
- взрослому без родительской роли право выдаётся отдельно;
- неизвестный Telegram ID не получает даже список домашних MAC-адресов;
- подробный сетевой инвентарь отправляется только в личный чат родителя, если
  пользователь явно не разрешил показывать его в семейной группе.

Бот не отвечает «интернет включён» сразу после отправки API-команды. Он сначала
применяет изменение, повторно читает профиль и устройства из RouterOS и только
затем подтверждает фактический результат. При ошибке бот сообщает, что именно
не изменилось, и выполняет целевой откат, когда он возможен. Повторно
доставленный Telegram Update имеет тот же operation ID и не продлевает доступ
ещё раз.

Временное разрешение или блокировка содержит сохранённое время окончания и
предыдущее состояние. Оно переживает перезапуск Home Assistant и автоматически
возвращает обычное расписание. Где это поддерживается безопасно, окончание
фиксируется также на стороне RouterOS, чтобы доступ не остался открытым только
из-за недоступности Home Assistant. Если для конкретной версии или топологии
RouterOS это обеспечить нельзя, мастер явно предупреждает пользователя и не
выдаёт временный override за автономно гарантированный.

Статусный ответ показывает профиль, активное правило, временное исключение,
следующее изменение и устройства участника, но не раскрывает пароль RouterOS,
полный токен бота или другие секреты. Все Telegram-операции попадают в общий
журнал решений с инициатором, причиной и результатом read-back.

### 8.6. Неизвестные устройства

Режимы:

- **наблюдение** — показать и уведомить;
- **карантин интернета** — запретить маршрутизируемый доступ, сохранив
  возможность администратору разобраться;
- **строгий список** — пропускать только подтверждённые устройства.

Строгий режим включается только после предпросмотра и проверки защищённых
устройств. В неизменяемый защитный набор входят сам роутер, Home Assistant,
точки доступа, управляющий компьютер/телефон и заданные аварийные устройства.

Реализация зависит от топологии:

- Wi-Fi access list работает только на точке доступа MikroTik;
- если MikroTik видит клиентов только после другого NAT, отдельных MAC у него
  может не быть;
- `static-only` DHCP сам по себе не останавливает устройство с вручную заданным
  IP;
- IPv4 и IPv6 должны контролироваться согласованно;
- MAC можно подменить, поэтому allowlist является средством порядка и
  родительского контроля, но не строгой аутентификацией.

Если условия не выполнены, интеграция блокирует включение строгого режима и
объясняет причину. Для настоящей изоляции рекомендуется отдельная гостевая или
карантинная VLAN; автоматическое перестроение VLAN не входит в первый релиз.

### 8.7. Карточка MikroTik

Карточка показывает:

- доступность и версию RouterOS;
- количество известных, неизвестных, динамических и статических устройств;
- список клиентов с IP, MAC, производителем, источником имени и уверенностью;
- предлагаемые совпадения Home Assistant;
- мастер статических лизов;
- профили участников и текущее состояние Kid Control;
- временную паузу/разрешение;
- последние изменения и ошибки проверки.

Все массовые и потенциально отключающие операции требуют отдельного
подтверждения с точным diff.

### 8.8. Защита RouterOS

- секреты не попадают в состояния сущностей, диагностику или журнал;
- сертификат проверяется, либо пользователь явно принимает локальный
  самоподписанный сертификат;
- перед изменением сохраняется точный снимок затрагиваемых записей;
- после изменения выполняется read-back;
- ошибочное или частичное применение запускает целевой откат;
- полные RouterOS backup содержат чувствительные данные и не создаются без
  отдельного решения пользователя;
- обновление RouterOS, перезагрузка, сброс, произвольный firewall и управление
  пользователями не входят в возможности модуля.

## 12. Техническая архитектура

Публичный репозиторий содержит одну интеграцию и весь обязательный runtime:

```text
custom_components/family_assistant/
  __init__.py
  manifest.json
  config_flow.py
  coordinator.py
  models/
  storage/
  permissions/
  messaging/
  shopping/
  tasks/
  alarms/
  court/
  routines/
  calendar/
  conversation/
  notifications/
  mikrotik/
  diagnostics.py
  repairs.py
  migrations/
  frontend/
  translations/
```

Архитектурные правила:

- один Config Entry на семейное пространство;
- отдельные менеджеры модулей вместо монолитного контроллера;
- одна очередь входящих сообщений и один маршрутизатор намерений;
- каналы, LLM, поиск и RouterOS реализованы адаптерами;
- append-only журнал значимых изменений;
- версия схемы данных и идемпотентные миграции;
- сущности являются представлением данных, а не хранилищем больших журналов;
- долгие сетевые операции не блокируют цикл Home Assistant;
- выгрузка Config Entry полностью останавливает listeners и фоновые задачи.

## 13. Хранение и приватность

В публичном репозитории находятся только код, переводы, документация,
синтетические fixtures и сборочные файлы.

Локально хранятся:

- токены Telegram;
- URL и ключи LLM/поиска;
- RouterOS credentials и сертификаты;
- имена, связи и Telegram ID участников;
- списки, расписания, баллы и история;
- пользовательские правила и выученные формулировки.

Данные Config Entry и Home Assistant Store находятся вне каталога компонента,
поэтому HACS-обновление кода их не заменяет. Секретные поля маскируются в UI,
логах и diagnostics. Экспорт по умолчанию исключает секреты и персональные ID.

## 14. Надёжность и безопасность выполнения

Каждый изменяющий процесс проектируется как небольшая state machine:

- стабильный operation ID;
- сохранение намерения до внешнего вызова;
- повтор без двойного эффекта;
- контрольное чтение результата;
- отдельное состояние доставки уведомления;
- восстановление после рестарта;
- ограниченные повторы и эскалация;
- компенсация или откат, если они безопасны.

Тесты обязательны для:

- ролей и разрешений;
- отрицаний и неоднозначных команд;
- повторной доставки одного Telegram Update;
- перезапуска на каждом этапе процесса;
- ошибок Store и внешнего API;
- миграций и повторного запуска миграции;
- отсутствия секретов в diagnostics;
- локализации всех пользовательских строк;
- read-back и отката сетевых изменений.

## 15. Публичная поставка через HACS

Текущий приватный операционный репозиторий Home Assistant не публикуется.
Создаётся отдельный чистый репозиторий, рекомендуемое имя:

```text
Wave-is/home-assistant-family-assistant
```

Рекомендуемые название и лицензия:

- отображаемое имя: Family Assistant;
- домен: `family_assistant`;
- лицензия: MIT.

Публичный репозиторий является единственным источником кода. Локальная
установка обновляется из того же релизного артефакта:

```text
изменение → тесты → CI → prerelease/release → обновление локального HA через HACS
```

CI включает Python и frontend-тесты, lint/type checks, Hassfest, HACS Action,
проверку переводов, secret scanning и проверку состава релизного архива.

Версионирование следует SemVer. Alpha и beta помечаются prerelease. Обычный
GitHub Release создаётся только при зелёном CI и содержит changelog, инструкции
миграции и отката. После стабильного периода подаётся PR в основной каталог
HACS; до его принятия интеграция устанавливается как custom repository.

## 16. Миграция текущей локальной системы

Существующие Family Assistant и Family Court становятся источником требований
и мигрируются в один домен.

Порядок:

1. зафиксировать текущее поведение тестами;
2. создать чистое модульное ядро;
3. реализовать импорт старого YAML и Store;
4. скопировать задачи, покупки, будильники, участников, баллы и историю;
5. проверить количества, идентификаторы и связи;
6. оставить исходные Store и резервную копию;
7. запустить новую интеграцию в shadow/read-only режиме;
8. переключить обработчик Telegram и карточки;
9. проверить основные сценарии и откат;
10. только после приёмки отключить старые компоненты.

Миграция не переносит реальные локальные настройки в публичные fixtures.

## 18. Не входит в базовый проект

- общий облачный Telegram-бот разработчика;
- облачное хранение семейных данных разработчиком;
- автоматическое применение сгенерированного LLM патча;
- произвольное исполнение shell или RouterOS-команд из чата;
- замена системы пользователей и безопасности Home Assistant;
- автоматическая перезагрузка, обновление или сброс MikroTik;
- обещание строгой сетевой безопасности только по MAC;
- автоматическая перестройка VLAN и firewall без отдельного специализированного
  проекта и подтверждения.

## 19. Критерии успеха

- базовые команды и карточки работают без LLM;
- повтор одного события не создаёт второй эффект;
- активные процессы продолжаются после перезапуска;
- каждое изменение имеет инициатора, причину и проверенный результат;
- обновление HACS сохраняет все пользовательские данные;
- ни один secret scanner не находит локальных данных в релизе;
- все пользовательские строки доступны на RU, UK и EN;
- неподготовленный пользователь может создать бота и подключить группу по
  инструкции без стороннего ID-бота;
- MikroTik read-only onboarding не меняет маршрутизатор;
- пакетная статизация всегда имеет preview и read-back;
- строгий сетевой режим невозможно включить без защищённого списка и проверки
  топологии;
- локальная рабочая установка использует тот же публичный релиз, который
  доступен остальным пользователям.

### Этап 2. Переход к миграционному релизу (`v1-rc`)

1. **Отдельный миграционный путь из текущей локальной установки** в `v1`-конфиг,
   с сохранением исторических данных и без изменения live-конфига до завершённой
   проверки (`legacy-copy-wizard`, `legacy-preparation`).
2. **Отключение legacy-компонентов** только после shadow-запуска нового контура и
   подтверждённого отката к резервной копии.
3. **Сквозной upgrade-цикл**: изменение кода → CI → release package → install/upgrade
   в HA sandbox (`tools/build_release.py`, `tools/run_upgrade_acceptance.py`).
4. **Миграционный smoke-набор** для критических модулей: задачи, покупки,
   будильники, суд, расписание, сеть/Kid Control, дашборд.

Критерий готовности этапа: все сценарии migration smoke воспроизводимы без ручных
фиксов между релизами и повторяемы в чистом контексте.

### Этап 3. Пользовательский v1 (`v1.0`)

1. **Пул модулей без «скрытых зависимостей»**: каждый модуль работает из единого
   компонента и не требует отдельной локальной инфраструктуры.
2. **Полная публичная документация**:
   - setup на трёх языках,
   - карточка/сервисы/команды на трёх языках,
   - миграционный путь и rollback guide.
3. **Перформанс и стабильность**: регрессионная матрица для HA-сценариев, устойчивость
   к replay/restart, прозрачный incident-closure в уведомлениях.
4. **Синхронный релизный ритм**: `release.md`, версияция SemVer, контрольные теги и
   проверочный changelog для каждой публикации.

Критерий готовности этапа: интеграция проходит все обязательные сценарии из
`docs/implementation-status.md`, код и релизные артефакты воспроизводимы, а
домашние данные не участвуют в Git.
